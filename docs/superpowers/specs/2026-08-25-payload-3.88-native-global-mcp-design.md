# Payload 3.88 Native Global MCP Design

## Context

The admin application currently uses Payload 3.61.1. That MCP plugin version supports collection capabilities but does not expose Payload Globals as native MCP entities. SiteConfig access is therefore implemented with a custom resource and two custom tools.

Payload 3.88.0 supports Globals directly. A configured Global receives native `find` and `update` capabilities, API key permission fields, Payload-generated input schemas, localization parameters, and normal Payload access handling.

## Goals

- Upgrade the complete Payload dependency set in `apps/admin` to 3.88.0.
- Expose `site-config` through the MCP plugin's native `globals` configuration.
- Remove the custom SiteConfig MCP resource and read/update tools.
- Preserve the existing collection capabilities and Post/Page custom workflow tools.
- Keep the frontend application outside the Next.js compatibility changes required by the Admin upgrade.

## Non-Goals

- Upgrade the whole monorepo to Next.js 16.
- Change SiteConfig fields, localization rules, access control, or stored content.
- Automatically modify existing MCP API key documents.
- Replace the Post/Page task-oriented custom MCP tools.

## Dependency Strategy

All Payload packages in `apps/admin` will use the exact version `3.88.0` because the packages declare exact peer dependencies on `payload@3.88.0` and, where applicable, on other Payload packages at the same version.

The dependency changes are:

- `payload`: `3.88.0`
- `@payloadcms/db-mongodb`: `3.88.0`
- `@payloadcms/next`: `3.88.0`
- `@payloadcms/plugin-mcp`: `3.88.0`
- `@payloadcms/plugin-seo`: `3.88.0`
- `@payloadcms/richtext-lexical`: `3.88.0`
- `@payloadcms/storage-vercel-blob`: `3.88.0`
- `@payloadcms/ui`: `3.88.0`
- Admin `next`: `15.4.11`
- Root `react` and `react-dom`: `19.1.2`

Payload 3.88.0 supports selected Next.js 15 patch ranges and Next.js 16. The Admin application will use Next.js 15.4.11 to minimize framework-level change. `apps/www` and `packages/ui` will retain their current Next.js declarations.

## MCP Configuration

The MCP plugin configuration will add a native Global map:

```typescript
globals: {
	"site-config": {
		description: "Global site configuration and localized labels.",
		enabled: {
			find: true,
			update: true,
		},
	},
}
```

This generates native SiteConfig `Find` and `Update` permission checkboxes in the MCP API key editor. The MCP plugin will derive its tool schema from the Payload Global schema and automatically include localization parameters.

Existing MCP API keys will not have the new permissions enabled automatically because the generated checkboxes default to `false`. An administrator must enable SiteConfig `Find` and `Update` for each key that needs them.

## Custom MCP Cleanup

The following custom SiteConfig primitives will be removed:

- `site-config://current`
- `get_site_config`
- `update_site_config`
- Their registration exports and focused custom-tool tests

The shared MCP helpers remain because the Post and Page workflow tools still use them. The MCP server name, logging options, collection configuration, and remaining custom tools remain unchanged.

## Data and Security Behavior

No database migration is required. Payload Globals remain stored under the same `site-config` slug, and the MCP plugin only changes how the document is exposed to MCP clients.

Native MCP operations will use the plugin's API key permission checks and Payload Global access behavior. The implementation will not introduce `overrideAccess: true` in project-owned custom code. Existing custom SiteConfig permission fields may remain in stored API key documents but will no longer be part of the active Payload schema or authorize a tool.

## Testing and Verification

Implementation will follow a focused red-green cycle:

1. Add a test that requires a native `site-config` Global configuration with `find` and `update` enabled.
2. Run the focused test and confirm it fails because the native configuration does not exist.
3. Add the native configuration and remove custom SiteConfig registrations.
4. Run the focused MCP tests.
5. Install the coordinated dependency versions and update the lockfile.
6. Regenerate Payload types if the running development process has not already done so.
7. Run all Admin tests, Admin TypeScript checking, and an Admin production build.
8. Inspect the dependency tree for peer dependency conflicts and confirm that SiteConfig appears as a native MCP permission group.

## Rollback

Rollback is performed through version control: restore the previous dependency declarations, lockfile, custom SiteConfig MCP implementation, and generated types. This design does not delete or transform SiteConfig content, so no content rollback is required.

## Acceptance Criteria

- Every Payload package used by `apps/admin` resolves to 3.88.0.
- The Admin application resolves a Payload-compatible Next.js and React version without peer dependency errors.
- `site-config` is configured under the MCP plugin's native `globals` option with `find` and `update` enabled.
- The custom SiteConfig resource and tools are no longer registered.
- Existing collection capabilities and Post/Page custom tools remain registered.
- Generated types include the native SiteConfig MCP permission group.
- Admin tests, type checking, and production build complete successfully.
